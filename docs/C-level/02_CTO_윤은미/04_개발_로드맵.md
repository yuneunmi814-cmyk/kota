# 10. 주간 리듬 (COO 운영 체계와 연동)

- 회의는 **주 3회**(08-03 결정). CTO는 회의마다 **"지난 회의 이후 커밋 + 지금 막힌 것"** 만 보고한다
- 막히면 시트 상태를 **`1-막힘`** 으로 바꾼다. 말로 설명하지 않는다 (COO §6-1-②)
- 회의록 정리는 **COO 담당**. CTO는 녹취만 전달한다

# 이 문서를 작성하면서 발견한 개선점

**① 로드맵을 쓰려면 제품 정의가 먼저 고정돼야 한다.**
이 문서를 세 번 다시 썼다. "3축이면 이렇게, 축제 단일이면 저렇게"가 계속 갈라졌기 때문이다. **그런데 그 결정은 7/22에 이미 내려져 있었고 `CLAUDE.md` 한 줄에만 적혀 있었다.** 미결정보다 나쁜 것이 **미전달**이다 — 미결정은 누군가 다시 묻지만, 미전달은 아무도 묻지 않는다.

**② "안 하는 것"을 적는 데 시간이 더 걸렸다.**
할 일 목록은 쉽게 나온다. 그런데 D-48에서 진짜 어려운 건 **거절 목록**이다. §8을 적고 나서야 S1이 9.5일로 줄었다. 적기 전에는 모든 게 다 들어 있었다.

**③ 가장 급한 일이 가장 작은 일이었다.**
S0-1(DB 만료일 확인)은 30분짜리인데 이 로드맵에서 실패 시 손실이 가장 크다. **작업량과 중요도는 상관이 없다.** 큰 작업부터 시작하려는 본능을 이 표가 막아준다.

**④ 60%라는 숫자를 적었더니 계획이 정직해졌다.**
가용시간을 안 적으면 언제나 100% 계획을 세우고 언제나 늦는다. 숫자를 적으니 S1이 이미 빠듯하다는 게 보였고, 그래서 범위 조정 규칙을 미리 정할 수 있었다. **늦은 뒤에 무엇을 뺄지 정하면 항상 잘못된 걸 뺀다.**
