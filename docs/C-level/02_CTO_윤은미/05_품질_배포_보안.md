## 2-1. CTO가 COO에게 요청하는 것

1. **재현 절차 + 재현율**(5/5·2/10)이 없으면 착수하지 않는다. 되묻는 왕복이 하루를 먹는다

# 7. 배포·복구 절차 (버스 팩터 완화) ★

> **CTO가 못 움직이는 상황에서도 팀이 배포를 되돌릴 수 있어야 한다.** COO §4-7-2("CTO 단일 의존")에 대한 CTO의 대응.

## 7-1. 웹 롤백

GitHub Pages는 이전 배포 아티팩트로 되돌릴 수 없다. **직전 커밋으로 revert 후 재배포**가 유일한 경로다.

```bash
git revert <문제 커밋> && git push
```

→ `deploy-web.yml`이 자동으로 재배포한다. (**push 권한은 CTO 전담이므로 실질적으로 CTO만 가능** — 이것이 남은 리스크다)

## 7-2. 백엔드 롤백

Render 대시보드 → 해당 서비스 → Deploys → 이전 배포 **Rollback**. **웹 콘솔에서 가능하므로 COO도 수행할 수 있다.**

## 7-3. 데이터 복구

시드 데이터가 레포에 있으므로 DB가 비어도 복구 가능하다.

```bash
npm run seed:prod    # backend/prisma/seed-*.json 기준 재적재
```

Render Docker CMD가 기동 시 `prisma migrate deploy && npm run seed:prod`를 자동 실행하므로 **재배포만으로 복구된다.**

## 7-4. 웹만 살리기 (최후 수단)

백엔드가 완전히 죽어도 `web/public/data/*.json` 정적 폴백으로 **축제 416건이 그대로 노출된다.**
즉 **최악의 경우에도 심사관에게 백지 화면은 보이지 않는다.** 이건 설계상 이미 확보된 안전망이다.

# 이 문서를 작성하면서 발견한 개선점

**① 우리 팀은 테스트를 잘 짜는데 잘못된 곳에 짰다.**
백엔드 통합 테스트 97개는 3인 팀에서 보기 드물게 좋다. 그런데 그중 29개가 **꺼둔 기능**을 지키고, 심사 제출물인 웹은 테스트도 CI도 0이다. **품질 투자는 총량이 아니라 방향이다.**

**② 최악의 시나리오가 이미 방어되어 있었다.**
정적 폴백 3단은 콜드스타트 대응으로 만들었는데, 결과적으로 **"백엔드가 완전히 죽어도 심사관에게 화면은 보인다"** 는 훨씬 큰 보험이 됐다. 의도하지 않은 안전망이지만 이제 알았으니 **의도적으로 유지**한다. (그리고 검색에만 이게 없다는 것도 이제 안다)

**③ QA 체크리스트가 없는 기능을 검증하고 있었다.**
COO가 성실하게 라인 로그인·식당·교통을 점검하려 했는데 셋 다 웹에 없다. **잘못된 정보는 게으름보다 비싸다** — 성실한 사람의 시간을 정확히 낭비시키기 때문이다. 기능 인벤토리(`03_제품_기능_현황.md`)를 배포마다 갱신하는 이유다.

**④ 롤백 절차를 쓰다가 버스 팩터를 다시 확인했다.**
백엔드는 Render 웹 콘솔로 누구나 되돌릴 수 있는데, **웹은 git push가 필요해서 CTO만 가능하다.** push 전담 규칙(08-03)이 충돌은 막지만 단일 장애점을 만든다. 지금은 수용하되 **이 트레이드오프를 알고 수용하는 것**과 모르고 당하는 것은 다르다. → ADR-005
