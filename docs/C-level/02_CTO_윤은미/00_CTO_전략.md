# 1. 문서 목적

07-29 오프사이트에서 합의된 *"각자 본인 포지션 관점의 MD 파일 작성 → 폴더로 통합 → 교차 검토 → 기능 개발"* 에 대한 CTO 문서다.

본 문서는 세 가지를 다룬다.

1. **CTO는 무엇을 책임지는가** (역할·경계)
2. **제품의 기술 상태는 실제로 어떠한가** (레포 실측 진단)
3. **그래서 9/21까지 무엇을 만드는가** (개발 우선순위)

> **작성 원칙** — COO 문서와 동일하게 간다. `(작성 예정)`·`예시`를 남기지 않는다. 모든 수치는 레포에서 뽑은 실측이며 근거 파일 경로를 명시한다. 확인하지 못한 것은 추측으로 채우지 않고 **`미확인`** 이라고 쓴다.
>
> **CTO 문서의 추가 원칙 하나 —** *"문서가 코드보다 앞서 쓰이지 않는다."* 아직 없는 기능을 있는 것처럼 쓰지 않는다. 문서-제품 괴리(COO §4-4)가 정확히 그렇게 생겼다.

# 2. 조직 컨텍스트

| 포지션 | 담당 | 책임 | 없으면 |
|---|---|---|---|
| **CTO** | **윤은미** | **제품·기술** | 물건이 안 나옴 |
| COO | 최용우 | 실행·품질·기록·자원 | 날짜를 놓치고, 왜 그렇게 정했는지 아무도 모름 |
| CMO | 전도준 | 수요·브랜드 | 아무도 모름 |

파이프라인은 병렬이 아니라 **순차 의존**이다 (COO §3-3).

```
전도준(기획·디자인)  →  윤은미(개발·배포)  →  최용우(QA·버그)
```

CTO는 이 사슬의 **한가운데**에 있다. 앞이 막히면 만들 것이 없고, 내가 막히면 뒤가 볼 것이 없다.
따라서 CTO가 관리해야 할 지표는 커밋 수가 아니라 **"지금 큐에 확정된 요구사항이 있는가"** 다.

# 3. CTO 정의

> **CTO = 확정된 것을 실제로 도는 물건으로 만들고, 그것이 계속 돌게 만드는 사람.**

## 3-1. 미션 (한 줄)

> "조직의 아이디어와 자동화 요구를 **동작하는 제품**으로 구현하고, 그 기술 기반을 **심사·확장·유지보수가 가능한 상태**로 유지한다."

## 3-2. 업무 5축

| # | 축 | 내용 | 지금 비중 |
|---|---|---|---|
| ① | **기능 개발** | 확정 요구사항 → 코드 → 배포 | **최대** |
| ② | **데이터 파이프라인** | 공공 API 수집·정규화·갱신. 데이터 활용 20점의 실체 | 높음 |
| ③ | 아키텍처·기술선택 | 스택 결정, 비용 통제, 확장 가능성 확보 | 중간 |
| ④ | 품질 기반 | 테스트·CI·배포 자동화. QA는 COO가 돌리되 **돌릴 판은 CTO가 깐다** | 중간 |
| ⑤ | 기술 기록 | 왜 그렇게 만들었는지 남긴다 (→ `06_기술_의사결정_기록.md`) | 낮음, 그러나 필수 |

핵심 신호는 하나다 — **"심사관이 URL을 열었을 때 동작하는가."**

## 3-3. 책임지지 않는 것 (경계) ★

> COO가 *"개념이 포괄적이면 범위가 무한히 넓어진다"* 를 지적했다(COO §3-2). CTO도 같다.
> **3인 스타트업 · D-48** 전제를 명시해 범위를 좁힌다.

| 안 하는 것 | 이유 | 대신 하는 것 |
|---|---|---|
| **제품 방향 단독 결정** | 3인 합의 사항 | 기술적 실현 비용을 숫자로 제시 |
| **마케팅 카피·비주얼 콘셉트** | CMO 영역 | 요구사항을 구현 가능 단위로 되묻기 |
| **일정·자료 관리** | **08-03 확정 — COO 영역** | 커밋 로그·배포 이력 제공 |
| **회의록 정리** | **08-03 이관 — COO 담당** | 녹취 원본 전달 |
| **버그 발견 자체** | COO의 QA 루프 | 재현 가능한 리포트를 받아 고치는 것 |
| **완벽한 아키텍처** | D-48에 리팩터링할 시간 없음 | 심사 경로를 우선 튼튼히, 나머지는 부채로 명시 기록 |

특히 마지막 줄이 중요하다. **지금은 "잘 만들 때"가 아니라 "끝낼 때"다.** 기술적으로 아쉬운 선택은 `06_기술_의사결정_기록.md`에 사유와 함께 남기고 넘어간다.

## 3-4. git 권한 (08-03 확정) ★

| 역할 | 권한 |
|---|---|
| **CTO(윤은미)** | **push 전담** |
| COO · CMO | **pull만** |

> 다중 push 충돌 방지. COO·CMO가 만든 문서는 CTO에게 전달되어 CTO가 push한다.
> **따라서 레포의 상태는 CTO의 책임이다.** 남이 올린 게 섞여 깨졌다는 변명이 성립하지 않는다.

## 4-8. 인프라 리스크 — 심사 당일 직결 ★

| 항목 | 실측 | 심사 리스크 |
|---|---|---|
| Render **free 플랜** (DB·Redis·API 전부) | `render.yaml` 주석 *"무료 플랜은 체험용·웹 슬립·DB 90일"* | **15분 무접속 시 슬립 → 콜드스타트 약 50초** |
| 대응책 | `keepalive.yml` cron `*/5`로 `/health` 핑 | 워크플로 주석이 *"GitHub 예약은 지연될 수 있음"* 이라고 한계를 자백 |
| 프론트 방어 | API 6초 타임아웃 → 정적 JSON 폴백 3단 | 축제 목록은 살지만 **검색은 폴백 없음** |
| **DB 90일 만료** | free PostgreSQL | **최초 생성일 미확인 → 즉시 확인 필요.** 심사 기간 중 만료되면 전멸 |
| JWT 키 영속성 | `keys/*.pem`을 볼륨 없이 컨테이너에 생성 | **재배포마다 전 세션 무효화** |
| CORS | `app.use(cors())` — origin 무제한 | 감점 요인은 아니나 명백한 구멍 |
| 5xx 로깅 | `if (!isProd) console.error(err)` | **운영 장애 원인 추적 불가** ← 심사 중 장애 시 치명 |

> **`DB 90일 만료일`이 이 표에서 가장 급하다.** 하나 확인하는 데 5분이고, 틀리면 프로젝트가 끝난다.

# 이 문서를 작성하면서 발견한 개선점

**① "더 개발할 게 없다"는 말은 코드량 기준의 착시였다.**
13.8k LOC 중 심사 대상 웹은 846줄(6%)이다. 나머지 94%는 심사관이 보지 않는다. **자산의 크기와 제출물의 완성도는 별개**이며, 우리는 큰 자산을 갖고 얇은 제출물을 내려던 참이었다.

**② 문서 정합성 붕괴는 CTO 쪽에도 있었다.**
COO는 CMO 문서의 불일치를 지적했지만, **README도 틀려 있다** — 라인 로그인 미구현, 테스트 수 3종 혼재, Render 주소 구버전. CTO가 push 전담이므로 이건 전적으로 CTO 책임이다. §5-4 동기화 지점에 **README 검증**을 포함시켜야 한다.

**③ 기능을 숨긴 판단은 옳았지만 기록이 없었다.**
7/22 검색 UI 숨김은 커밋 메시지 한 줄로만 남았고, **왜 숨겼는지(=검색에 축제가 빠져 있음)는 어디에도 없었다.** 그래서 08-03에 COO가 "검색이 없다"고 다시 발견했고, 오늘 코드를 다시 열어봐야 했다. 이것이 `06_기술_의사결정_기록.md`를 만든 이유다. **끈 채로 두는 것보다 왜 껐는지 남기는 것이 중요하다.**

**④ 테스트는 잘 만들었는데 잘못된 곳에 만들었다.**
백엔드 97개 통합 테스트는 3인 팀 기준 과할 정도로 좋다. 그런데 그 테스트 중 29개가 **비활성 상태인 마켓플레이스**를 지키고, 심사 제출물인 `web/`은 **테스트도 CI도 0**이다. 노력의 배분이 심사 배점과 반대로 되어 있었다.
