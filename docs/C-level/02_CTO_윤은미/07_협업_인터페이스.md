# KOTA — 협업 인터페이스 (CTO)

> CTO가 COO·CMO와 **무엇을 주고받는지**, 코드·이슈·문서를 **어떤 규약으로 다루는지** 정의한다.
> 운영 규칙의 단일 출처는 COO 문서다. **여기서는 CTO 쪽 인터페이스만 정의하고, COO 규칙을 다시 쓰지 않는다.**
>
> **작성** · 윤은미(CTO) · **일자** · 2026-08-04

---

# 1. 인터페이스 요약

```
       ┌──────────── CMO 전도준 ────────────┐
       │  기획·디자인·타겟·메시지            │
       └───────────┬────────────────────────┘
                   │ ① 확정된 요구사항 (기획·시안)
                   ▼
       ┌──────────── CTO 윤은미 ────────────┐
       │  구현·배포·데이터·기술기록          │
       │  ★ git push 전담                   │
       └───────────┬────────────────────────┘
                   │ ② 배포 알림 + 변경 요약
                   ▼
       ┌──────────── COO 최용우 ────────────┐
       │  QA·일정·기록·자료                 │
       └───────────┬────────────────────────┘
                   │ ③ 재현 가능한 버그 리포트
                   └────────→ CTO (다시 위로)
```

**세 화살표가 전부다.** 이 셋이 끊기면 파이프라인이 멈춘다 (COO §3-3).

# 2. ↔ CMO (전도준) — 요구사항 인터페이스

## 2-1. CTO가 받는 것

| 항목 | 형태 | 없으면 |
|---|---|---|
| 화면 시안 | 이미지 또는 설명 | 임의로 만들고 나중에 다시 만든다 |
| **기능의 목적** | 한 줄 — *"사용자가 무엇을 할 수 있어야 하는가"* | 기술적으로 맞지만 쓸모없는 걸 만든다 |
| 우선순위 | 다른 것과 비교한 순위 | 전부 급한 것이 된다 |

## 2-2. CTO가 돌려주는 것

| 항목 | 형태 |
|---|---|
| **구현 비용** | **일 단위 숫자.** "어렵다/쉽다"로 답하지 않는다 |
| 기술적 제약 | *"이건 데이터에 없다"* / *"이건 API가 안 준다"* |
| 대안 | 요구를 못 들어줄 때 **반드시 대안과 함께** (팀 협업규칙: *의견엔 근거·대안 필수*) |

## 2-3. 규칙 ★

> **CTO는 "무엇을 만들지"를 정하지 않고, "얼마나 드는지"를 정확히 말한다.**

- 확정되지 않은 기획은 **큐에 넣지 않는다.** 만들다 바뀌면 그 시간이 통째로 사라진다
- 기획서와 코드가 다르면 **코드가 옳다**(COO §5-4). 다만 **다르다는 사실을 CTO가 먼저 알린다** — 이번에 5건이 쌓인 이유가 이걸 안 해서다
- 디자인 시안이 없으면 **기존 디자인 토큰**(`--color-green #004027` 등)으로 만들고 나중에 조정한다. 시안을 기다리며 멈추지 않는다

# 3. ↔ COO (최용우) — 품질·일정 인터페이스

## 3-1. CTO → COO

| 시점 | 전달물 |
|---|---|
| 배포할 때마다 | **배포 알림 한 줄** — 무엇이 바뀌었고 무엇을 봐줬으면 하는지 |
| 주 1회 | `git log --since=<지난 회의>` 출력 (COO §5-4 문서-제품 대조용) |
| 회의 후 | **녹취 원본** (회의록 정리는 COO 담당 — 08-03 이관) |
| 기능이 추가/숨김될 때 | **기능 인벤토리 갱신** (`03_제품_기능_현황.md`) |
| 지출 발생 시 | 항목·금액·증빙 (COO §9-2 회계) |

## 3-2. COO → CTO

| 항목 | 형태 |
|---|---|
| 버그 | **GitHub Issue** — 재현 절차 + 재현율 + 환경 + 콘솔 원문 |
| 일정 | 시트 `팀_할일` (CTO는 **읽고 상태만 바꾼다**) |
| 자료 요청 | 디스코드 |

## 3-3. CTO의 의무는 하나다 ★

> **막히면 시트 상태를 `1-막힘`으로 바꾼다.**

COO §6-1-②의 규칙이다. *"저 막혔어요"* 라고 말하기는 어렵지만 **드롭다운을 바꾸는 건 쉽다.**
CTO는 데일리 보고를 하지 않는다. 주 3회 회의로 충분하다.

## 3-4. 즉시 정정 요청 (S0-5) ★

COO의 QA 체크리스트에 **존재하지 않는 기능**이 3개 있다. 그대로 두면 COO가 없는 걸 찾느라 시간을 쓴다.

| 항목 | 실제 | 조치 |
|---|---|---|
| 라인(LINE) 로그인 | 백엔드에도 웹에도 **코드 0줄** | 체크리스트에서 제거 |
| 식당 탭 | **웹에 라우트 없음** | 제거 (08-04 제품 축 결정 후 확정) |
| 교통 | **웹에 라우트 없음** | 제거 (동일) |

> **잘못된 정보는 게으름보다 비싸다.** 성실한 사람의 시간을 정확히 낭비시키기 때문이다.

# 4. git 규약

## 4-1. 권한 (08-03 확정)

| 역할 | 권한 |
|---|---|
| **CTO** | **push 전담** |
| COO · CMO | pull만 |

COO·CMO가 만든 문서는 **CTO에게 전달 → CTO가 push.** 따라서 **레포 상태는 전적으로 CTO 책임**이다.

> ⚠️ **비용을 알고 수용한다** — 웹 롤백은 git push가 필요해 **CTO만 가능**하다. 단일 장애점이다 (ADR-005).

## 4-2. 커밋 메시지

기존 규약을 유지한다 — `type(scope): 한국어 요약`

```
feat(festivals): 축제 소스 2개 통합 + 전국 커버 — 121 → 416건
fix(web): 지역 배너 폴백에서 미매핑 slug 제거
docs(공모전): 2026-07-29 오프사이트 회의록 추가
chore(deploy): Render 블루프린트를 kota 서비스명으로 갱신
```

- `type` — `feat` `fix` `docs` `chore` `refactor` `test`
- **수치 변화는 메시지에 넣는다** (`121 → 416건`). 나중에 `git log`만으로 히스토리가 읽힌다
- **기능을 끄거나 숨길 때는 이유를 쓴다** (ADR-004 규칙)

## 4-3. 브랜치

- 기본은 `main` 직접 작업 (3인, 실질 커밋 1인)
- **위험한 변경**(마이그레이션·배포 설정·플래그 ON)은 브랜치 + PR로 CI를 태운다
- PR이 있으면 `ci.yml` 4개 잡(backend·**web**·admin-web·mobile)이 전부 그린이어야 머지

## 4-4. 무엇을 레포에 넣는가

COO §5-1 배치표를 따른다. **CTO 관점의 요약:**

| 넣는다 | 안 넣는다 |
|---|---|
| 코드 · 마이그레이션 · 시드 데이터 | **데일리 리포트** (시트) |
| 회의록 전문 (`docs/`) | **할 일 목록** (시트) |
| 기술 문서 · ADR | 대용량 원본(PDF·영상) → 구글 드라이브 |
| 워크플로 · 설정 | **`.env` · `keys/*.pem`** (gitignore 확인 완료) |

> **단타성 데이터를 git에 넣으면 push/pull 빈도가 과도해진다** (08-03 결정). push가 CTO 전담이므로 그 부담은 전부 CTO에게 온다.

# 5. GitHub Issue 규약

> **현재 이슈 0건.** COO의 QA 루프가 한 바퀴도 안 돌았다 (COO §4-6). 이제 시작한다.

## 5-1. 라벨

| 라벨 | 의미 |
|---|---|
| `P0` | 서비스·데모 불가 → **즉시** |
| `P1` | 핵심 기능 파손 |
| `P2` | 우회 가능 |
| `P3` | 사소 |
| `area:web` `area:backend` `area:data` `area:infra` | 영역 |
| `blocked` | 외부 요인으로 막힘 |
| `wontfix` | 안 고침 (**사유 한 줄 필수**) |

## 5-2. 흐름

```
COO가 이슈 생성 (재현 절차 포함)
   ↓
CTO가 라벨·우선순위 부여
   ↓
CTO 수정 → 커밋에 `fix #N`  → 이슈 자동 종료 방지 위해 커밋은 참조만
   ↓
배포 후 CTO가 "배포됨" 코멘트
   ↓
COO가 재확인 후 **직접 닫는다** (리포터가 닫는 원칙)
```

## 5-3. CTO가 지킬 것

1. **재현 안 되면 착수하지 않는다.** *"재현 절차 부탁드립니다"* 코멘트 후 대기
2. **안 고칠 것은 `wontfix` + 사유**로 닫는다. 열려만 있는 이슈는 노이즈다
3. **한 이슈 한 버그** — COO가 묶어 올리면 CTO가 쪼갠다
4. 심사 관련 이슈는 **P0/P1로 승급**한다. 사용성 사소함보다 심사 배점이 우선이다

# 6. 문서 동기화 규칙 ★

문서-제품 괴리 5건이 생긴 이유는 **동기화 지점이 없어서**였다. CTO 쪽 장치를 명시한다.

| 시점 | 대조 | 담당 |
|---|---|---|
| **배포할 때마다** | 배포 기능 vs `03_제품_기능_현황.md` | **CTO** |
| 주 1회 회의 | `git log` vs 전략 문서 | CTO가 로그 제공, COO가 대조 |
| **기능을 끄거나 숨길 때** | ADR 추가 + `features.ts` 주석 | **CTO** (ADR-004 규칙) |
| 월 1회 | 전략 문서 세트 상호 정합성 | 전원 |
| **README 검증** ★ | README 서술 vs 실제 코드 | **CTO** — 이번에 4곳이 틀려 있었다 |

> **규칙: 레포와 문서가 다르면 레포가 옳다. 단, 다르다는 사실을 CTO가 먼저 알린다.**

# 7. 커뮤니케이션 채널 (CTO 관점)

COO §6-1-③ 응답 기대시간을 CTO 입장에서 다시 쓰면 다음과 같다.

| 상황 | 채널 | CTO 응답 |
|---|---|---|
| 서비스 다운 · 데모 불가 (P0) | 카톡 멘션 | **즉시** |
| 버그 리포트 (P1~P3) | GitHub Issue | 48시간 내 라벨링 |
| 기획·기술 논의 | 디스코드 | 48시간 |
| 현황 확인 | **시트를 볼 것** | — |

> *"진행 어때요?"* 를 없애는 것이 CTO가 가장 크게 얻는 시간이다. 그러려면 **CTO가 시트를 정직하게 유지**해야 한다. 거래다.

# 8. CTO가 팀에 요청하는 3가지

1. **확정되지 않은 것을 개발 큐에 넣지 말아 달라.** 만들다 바뀌면 그 시간은 복구되지 않는다
2. **버그는 재현 절차와 함께 달라.** 되묻는 왕복 한 번이 하루다
3. **"이거 되나요?"보다 "이거 며칠이에요?"로 물어봐 달라.** 대부분은 되고, 문제는 언제나 시간이다

# 이 문서를 작성하면서 발견한 개선점

**① 인터페이스를 정의하니 내 책임 범위가 오히려 줄었다.**
"CTO는 무엇을 만들지 정하지 않는다"를 명시하니, 기획 미결정 상태에서 혼자 추측해 만들던 패턴이 문제로 보였다. **7월에 혼자 리브랜딩·MVP·배포까지 간 것은 성과이자 동시에 위험 신호**였다 — 아무도 확정해 주지 않아서 혼자 정하며 갔고, 그래서 문서와 어긋났다.

**② 잘못된 문서가 남의 시간을 쓰게 만든다.**
COO가 라인 로그인·식당·교통을 QA하려고 준비했다. 셋 다 없다. 문서 오류는 쓴 사람이 아니라 **읽은 사람의 시간을 태운다.** 그래서 §6에 README 검증을 CTO 정기 업무로 넣었다.

**③ push 전담은 충돌을 막는 대신 병목을 만든다.**
백엔드는 Render 콘솔로 누구나 롤백할 수 있는데 웹은 CTO만 가능하다. 지금은 수용하지만 **알고 수용하는 것과 모르고 당하는 것은 다르다.** ADR-005에 재검토 조건(*"CTO 부재로 롤백 지연이 1회라도 발생하면"*)을 붙여뒀다.
