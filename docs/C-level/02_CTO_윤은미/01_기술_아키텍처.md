# 2. 워크스페이스 4개

`package.json`이 4개, `package-lock.json`도 4개다. npm workspaces가 아니라 **독립 디렉토리 4개**를 한 레포에 둔 형태다.

| 워크스페이스 | 런타임/프레임워크 | 규모 | 배포 |
|---|---|---|---|
| `backend/` | Node ≥22 · ESM · Express 4.21 · TS 5.8 · **tsx로 TS 직접 실행(빌드 없음)** | 5,812 LOC + 테스트 1,472 | Render Docker (free) |
| `web/` | React 18.3 · Vite 5.4 · **Tailwind v4** · react-router 6.30 | 846 LOC | GitHub Pages |
| `admin-web/` | React 18.3 · Vite 5.4 · 자체 CSS | 1,696 LOC | Render static |
| `mobile/` | **Expo SDK 56** · RN 0.85.3 · React 19.2 · TS 6.0 | 3,517 LOC | EAS 수동 |

## 2-1. 왜 tsx로 직접 실행하는가

`backend`는 `tsc` 빌드 산출물 없이 `tsx`로 TS를 그대로 실행한다. Dockerfile CMD도 `prisma migrate deploy && npm run seed:prod && npm run start`다.

- **장점** — 빌드 단계 제거, 배포 파이프라인 단순화, 3인 팀에서 유지 비용 최소
- **비용** — 프로덕션 기동 시 트랜스파일 오버헤드, 타입 오류가 런타임까지 살아남을 수 있음
- **완화** — CI(`ci.yml`)에서 `typecheck`를 별도 잡으로 강제

> 판단은 `06_기술_의사결정_기록.md` ADR-002에 기록.

## 3-4. 캐시 · 세션 · 레이트리밋

| 계층 | 구현 | 파일 |
|---|---|---|
| 캐시 | Redis **5분 TTL** + `cachever:explore` 버전 범프 무효화 | `lib/cache.ts` |
| KV 추상화 | `REDIS_URL` 없으면 **인메모리 MemoryStore 폴백** (주석: *"개발·테스트 전용, 운영은 Redis 필수"*) | `lib/kv.ts` |
| 세션 | JWT **RS256** + Refresh Token Rotation | `lib/jwt.ts`, `modules/auth/session.ts` |
| 레이트리밋 | KV 기반 — 게스트 30/분, 로그인 60/분 (테스트 우회) | `middleware/rateLimit.ts` |

> ⚠️ **인메모리 폴백은 다중 인스턴스 스케일아웃을 불가능하게 만든다.** free 플랜 단일 인스턴스에서는 문제 없지만, 유료 전환 시 반드시 Redis를 붙여야 한다. server.ts가 기동 시 경고를 출력하고 있다.

## 6-2. CI (`.github/workflows/ci.yml`)

main push + 모든 PR에서 3개 잡:

| 잡 | 내용 |
|---|---|

## 6-3. keepalive (`.github/workflows/keepalive.yml`)

cron `*/5 * * * *`로 Render `/health` 핑 (최대 4회 재시도). free 인스턴스의 15분 슬립·약 50초 콜드스타트 회피용.
**워크플로 주석 자체가 *"확실한 가동시간은 외부 모니터 권장"* 이라고 한계를 인정하고 있다.**

## 6-4. 로컬 (`docker-compose.yml`)

db(postgis:16-3.4, 포트 5433) + redis:7-alpine + backend + seed 프로필. 데모용 `NODE_ENV=development`, `PG_PROVIDER=mock`.

# 7. 시크릿 관리

- 전부 `backend/src/config/env.ts`의 **zod 스키마로 검증되는 환경변수**. 코드 하드코딩 없음 (TourAPI 클라이언트에 *"코드에 박지 않는다"* 주석 명시)
- 키 이름 — `TOURAPI_SERVICE_KEY`(공공데이터 7종 공용) · `YOUTUBE_API_KEY` · `GEMINI_API_KEY` · `KAKAO_REST_API_KEY` · `GOOGLE_CLIENT_ID` · `KAKAO_ENABLED` · `PG_API_SECRET` · `PORTONE_WEBHOOK_SECRET` · `S3_BUCKET` · `FCM_PROJECT_ID`
- 키 미설정 시 각 기능이 **503으로 게이팅**(`Errors.notConfigured`) — 서버가 죽지 않는다
- `backend/.env`·`backend/keys/*.pem`은 로컬에만 존재하며 **`git check-ignore` 확인 결과 정상 제외**(`backend/.gitignore:3,4`). 추적되는 민감 파일은 `.env.example` 2개뿐. **레포에 커밋된 시크릿 없음**
- 배포 주입 — `render.yaml`의 `sync: false`(대시보드 수동 입력) · `deploy-web.yml`의 `VITE_API_BASE`

# 이 문서를 작성하면서 발견한 개선점

**① 아키텍처 문서가 없어서 매번 코드를 다시 읽었다.**
검색이 왜 꺼져 있는지, 폴백이 몇 단인지, 어떤 API를 쓰는지 — 전부 코드에 있지만 **꺼내는 데 매번 시간이 든다.** 3인 팀에서 CTO 혼자 아는 정보는 버스 팩터를 1로 고정시킨다. 이 문서 자체가 그 완화책이다.

**② 프론트 3개 중 심사 대상만 가장 얇다.**
모바일 3.5k · CMS 1.7k · 웹 0.85k. 자원 배분이 심사 배점과 반대로 되어 있다. 이건 아키텍처 문제가 아니라 **우선순위 문제**이며 08-04에 팀이 답할 사안이다.

**③ 게이팅 설계는 잘 되어 있다.**
키가 없으면 503, Redis가 없으면 인메모리, API가 죽으면 정적 폴백 — **부분 실패가 전체 실패로 번지지 않는 구조**가 이미 있다. 이건 심사 항목 *"안정성"* 에 그대로 쓸 수 있는 서술이므로 기능설명서에 반영한다 (→ `08_공모전_기술대응.md`).
