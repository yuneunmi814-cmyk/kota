> 심사 배점 **데이터 활용 적절성 20점**이 직접 걸린 문서. 어떤 공공 API를 어떻게 쓰고 있는지, 데이터가 실제로 얼마나 채워져 있는지, 무엇이 비어 있는지를 실측으로 기록한다.

# 1. 왜 이 문서가 중요한가

공고문 심사 기준에 **"데이터 활용 적절성 20점 — 공사 OpenAPI 활용 필수"** 가 있고, 공고문에 다음 문장이 있다.

> ⚠️ **제출한 인증키로 개발 기간 내 API 호출건수와 활용 내역을 확인한다.**

즉 **데이터 활용은 서술이 아니라 실측으로 검증된다.** "많이 썼다"고 쓰는 게 아니라 호출 로그가 남아 있어야 한다.
그리고 08-03에 CTO가 실사용 중 발견한 문제(*"영월·제천 축제가 코타에 없다"*)가 정확히 이 축의 문제다.

# 6. API 호출 실적 — 지금 집계가 안 된다 ★

공고문이 **"제출한 인증키로 개발 기간 내 호출건수와 활용 내역을 확인한다"** 고 못 박았는데, 우리는 **호출 횟수를 세고 있지 않다.**

| 항목 | 현재 | 필요 |
|---|---|---|
| 호출 카운트 | ❌ 없음 | 모듈별 누적 호출 수 |
| 호출 로그 | pino 로그에만 남고 집계 없음 | 기간별 집계 |
| 활용 API 목록 | 코드에는 있음, 문서 없음 | 제출용 표 (본 문서 §2가 초안) |
| 인증키 | CTO 보유 | **인코딩/디코딩 2종 모두** 정리 필요 |

**조치** — 공공데이터포털 마이페이지에서 **일별 호출 통계를 확인할 수 있다.** 별도 계측 코드를 만들 필요 없이 스크린샷·수치를 확보한다. (→ `04_개발_로드맵.md` S3)

> 단, **호출량 자체가 적으면 문제다.** 현재 sync는 수동이라 개발 기간 중 호출이 몇 번뿐일 수 있다.
> **주 1회 정기 sync를 GitHub Actions cron으로 돌리면** ① 데이터 신선도 ② 호출 실적 **두 문제가 동시에 해결된다.** → S1-D3

        ├─→ DB upsert

        └─→ 변경 요약을 디스코드 알림                        ← 신규 (COO 자동화 4순위와 연결)

# 이 문서를 작성하면서 발견한 개선점

**① 우리가 가진 카드를 우리가 몰랐다.**
관광공사 API를 7종이나 쓰고 있는데 어디에도 목록이 없었다. 데이터 활용 20점을 서술하려면 **먼저 우리 자신이 무엇을 쓰는지 알아야 한다.** 코드에 있는 것과 제출할 수 있는 것은 다르다.

**② "총량"으로 데이터를 보면 안 된다.**
416건이라는 숫자는 안심을 준다. 그러나 사용자는 전국을 보지 않고 **자기가 갈 도시 하나**를 본다. 08-03에 CTO가 축제에 직접 가서 발견한 것이 이거였고, 그 발견이 대시보드 숫자보다 정확했다. **실사용이 최고의 QA다.**

**③ 원인이 외부에 있어도 책임은 우리 것이다.**
제천 축제가 없는 건 공공데이터에 없어서다. 하지만 사용자에겐 "코타에 없는 것"이다. **남 탓으로 끝나는 리스크는 관리되지 않는다.** 그래서 §8에 "원본 미등록"을 우리 리스크로 올렸다.

**④ 정기 sync 하나가 문제 3개를 동시에 푼다.**
데이터 신선도 · API 호출 실적 · 심사 서술 근거. 작업량은 GitHub Actions 워크플로 파일 하나다. **비용 대비 효과가 이 로드맵에서 가장 큰 항목이다.**
