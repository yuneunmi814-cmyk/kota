# 2. 완성도 30점 — 기능성 · 안정성 · 편의성

## 2-1. 심사관이 실제로 하는 일

제출 항목 3번이 **"접속 가능한 웹 URL"** 이다. 즉 **심사관이 브라우저로 직접 들어온다.**
따라서 완성도 30점은 문서가 아니라 **그 순간의 화면**으로 결정된다.

| 심사관의 행동 | 지금 일어나는 일 | 조치 |
|---|---|---|
| URL 진입 | Render 슬립 시 **약 50초** → 6초 후 정적 폴백으로 화면은 뜸 | keepalive 유지 + 폴백 유지 (ADR-003·008) |
| 지역 배너 클릭 | **폴백 지역 3개(`goyang`·`jeonbuk`·`gyeongbuk`)는 결과 0** | **S1-F2** |
| 축제 검색 시도 | **검색 진입점이 없다** | **S1-F1** |
| 특정 도시 선택 | 제천 1건 · 영월 1건 · 공주 2건 | **S1-D1** |
| 같은 축제 두 번 보임 | 고양호수예술축제 중복 2건 | **S1-D2** |
| 언어 전환 (ja/th) | UI만 바뀌고 **축제명은 한국어** | **S2-1** |
| 새로고침 · 딥링크 | ✅ 정상 (`404.html` SPA 대응) | 유지 |
| 백엔드가 죽어 있음 | ✅ 정적 폴백으로 축제 416건 노출 | **강점으로 서술** |

## 2-2. 안정성 — 이건 우리 강점이다 ★

기능설명서에 **서술 가능한 실제 설계**가 있다.

> **부분 실패가 전체 실패로 번지지 않는 3중 방어**
> ① API 키 미설정 시 해당 기능만 503으로 게이팅 — 서버는 살아 있다
> ② Redis 없으면 인메모리 폴백 — 캐시 계층 장애가 서비스를 멈추지 않는다
> ③ 라이브 API 실패 시 정적 데이터 폴백 — **백엔드가 완전히 죽어도 축제 416건이 노출된다**

여기에 더해:
- 백엔드 **통합 테스트 97개** (실 PostGIS 컨테이너 + 앱 전체 호출)
- 전역 에러 핸들러 + 통일 에러 코드 체계 + 모든 async 핸들러 래핑 강제
- **JWT RS256 + Refresh Token Rotation**, 관리자 **TOTP MFA**, 레이트리밋
- 위치기반서비스사업 **신고 수리 완료(제1175호)**, 이용약관·개인정보처리방침·위치기반서비스이용약관 작성 완료

> **대부분의 공모전 출품작에 없는 것들이다.** 문제는 이걸 **아무 데도 안 적어놨다**는 것이었다.

## 2-3. 편의성

- 위치 기반 거리순 정렬 (커밋 `f0a46cb`) — **좌표 계산은 클라이언트에서, 위치는 서버로 보내지 않는다** (개인정보 관점 강점)
- 4개어 UI (ko/en/th/ja)
- 모바일 우선 반응형
- ⚠️ **검색 부재가 편의성의 가장 큰 구멍** → S1-F1

## 3-1. 공고문의 검증 방식

> ⚠️ **"제출한 인증키로 개발 기간 내 API 호출건수와 활용 내역을 확인한다."**

**서술이 아니라 실측으로 검증된다.** 두 가지가 필요하다 — ① 활용 API 목록 ② 실제 호출 실적.

## 3-3. 서술 포인트 — "많이"가 아니라 "왜"

심사관은 API 개수를 세지 않는다. **각 API가 왜 필요했는지**를 본다.

> **① 커버리지 문제를 2소스 병행으로 해결했다**
> CTO가 실제로 지역 축제에 갔는데 서비스에 없었다. 원인을 추적해 TourAPI 단독의 커버리지 한계를 확인하고, 전국문화축제표준데이터를 병행해 **121 → 416건**으로 확대했다. **실사용에서 발견해 데이터 소스로 해결한 사례다.**
>
> **② API 필터의 함정을 실측으로 찾아 우회했다**
> `searchFestival2`의 구형 `areaCode` 필터는 결과가 부실하다(**서울 2건 vs 법정동 코드 99건**). 이를 발견해 **법정동 코드 체계로 전환**했고, 2026-07 광주·전남 통합(`regnCd 12`)과 세종의 5자리 코드(`36110`)까지 반영했다.
>
> **③ 단순 조회가 아니라 랭킹 신호로 가공했다**
> DataLab 방문자수를 `visitorScore`로, YouTube 조회수를 `buzzScore`(로그 스케일)로 변환해 **인기 지역·트렌드 지역 랭킹**을 만든다. 공공데이터를 그대로 보여주는 게 아니라 **의사결정 신호로 재가공**했다.
>
> **④ 접근성 데이터를 포함했다**
> 반려동물 동반(`detailPetTour2`)·무장애 여행(`detailWithTour2`)을 연동해 **관광 취약계층까지 포괄**한다.

## 3-4. 호출 실적 확보 ★ (S1-D3 + S3-1)

| 문제 | 현재 | 조치 |
|---|---|---|
| sync가 **전부 수동** | 스케줄러 없음 (cron은 keepalive뿐) | **S1-D3 — GitHub Actions 주 1회 정기 sync** |
| 호출 횟수 미집계 | pino 로그에만 남음 | **공공데이터포털 마이페이지 일별 통계**로 확보 (별도 계측 불필요) |

## 4-2. API 개방 (확장성 서술)

08-03에 CMO가 언급한 *"우리도 나중에 API를 팔 수 있게끔 설계해야 한다"* 에 대한 기술 답변:

- 백엔드는 이미 **REST API(`/api/v1`, 약 85개 엔드포인트)** 로 분리되어 있고, 웹·모바일·CMS가 모두 이 API를 소비한다
- 즉 **외부 개방을 위한 구조 변경이 필요 없다.** 필요한 것은 ① API 키 발급 체계 ② 쿼터·과금 ③ 문서
- 발전 계획에 *"프론트-백엔드가 완전히 분리된 API 우선 설계 — 지자체·여행사 대상 데이터 개방이 구조적으로 가능"* 으로 서술

## 4-3. 지역 특화 가점 (+2점) — 데이터가 뒷받침해야 한다 ★

COO §10-3이 **공주(충남) 단독 지정**을 제안했다. 가점 +2 + 충남 RTO 특별상 후보.

**CTO 관점의 조건 하나** —

> **지역 특화는 문구가 아니라 그 지역의 데이터 밀도로 증명된다.**
> 현재 **공주 축제는 2건**이다. 심사관이 "공주 특화"를 읽고 공주를 눌렀을 때 2건이 뜨면 가점보다 감점이 크다.
> **공주를 특화 지역으로 정한다면 S1-D1에서 공주 데이터를 최소 5건 이상으로 채우는 것이 선행 조건이다.**

## 7-1. CTO가 답해야 할 예상 질문

| 질문 | 준비된 답 |

# 이 문서를 작성하면서 발견한 개선점

**① 우리가 가진 것 중 가장 강한 카드를 우리가 몰랐다.**
관광공사 API를 7종 + 표준데이터까지 쓰고 있는데 **목록이 어디에도 없었다.** 데이터 활용 20점은 우리가 가장 유리한 항목인데, 정리가 안 돼 있어서 그대로 두면 서술조차 못 할 뻔했다.

**② "안정성"을 서술할 재료가 이미 있었다.**
3중 폴백·503 게이팅·통합 테스트 97개·RS256·MFA·위치기반사업 신고 수리. 전부 심사 서술에 쓸 수 있는데 **기능이 아니라서 아무도 자랑할 생각을 안 했다.** 완성도 30점의 "안정성"이 정확히 이걸 본다.

**③ 지역 특화 가점은 마케팅이 아니라 데이터 작업이다.**
COO가 공주 단독 지정을 제안했을 때 처음엔 서류 문제로 봤다. 그런데 **공주 축제가 2건**이다. 가점 +2를 받으려고 심사관을 데이터가 빈 지역으로 안내하는 셈이 된다. **가점 신청 전에 그 지역 데이터를 채우는 게 선행 조건**이며, 이건 CTO 작업이다.

**④ 심사에서 가장 위험한 건 버그가 아니라 거짓말이다.**
"AI 개인화 추천"이 문서에 있고 코드에 없다. PT에서 한 번만 파고들면 무너진다. **없는 것을 없다고 쓰는 것이 완성도 점수를 지키는 방법**이다. 대신 있는 것(공공데이터 2소스 통합·규칙 랭킹·3중 폴백)을 제대로 서술한다.
