# 3. COO 정의

> **COO = 정해진 것이 실제로 굴러가게 만드는 사람.**

CTO는 만들고, CMO는 알리고, COO는 그 둘이 멈추지 않게 한다.

| 포지션 | 담당 | 책임 | 없으면 |
|---|---|---|---|
| CTO | 윤은미 | 제품·기술 | 물건이 안 나옴 |
| CMO | 전도준 | 수요·브랜드 | 아무도 모름 |
| **COO** | **최용우** | **실행·품질·기록·자원** | 만들긴 하는데 날짜를 놓치고, 왜 그렇게 정했는지 아무도 모름 |

## 3-1. 업무 5축

| # | 축 | 내용 |
|---|---|---|
| ① | **실행 관리** (비중 최대) | 결정사항에 담당·기한을 붙여 완료까지 추적. 병목을 뚫는다 |
| ② | 프로세스·시스템 | 두 번 반복되는 일은 규칙·템플릿·자동화로 고정. 성실성에 의존하지 않는다 |
| ③ | 품질·QA | 제품이 말한 대로 실제로 도는지 검증 (개발 트랙 RNR상 본업) |
| ④ | 자원·돈 | 지출 기록, 예산, 회계 장부 |
| ⑤ | 기록·측정 | 의사결정 히스토리·지표 |

핵심 신호는 하나다 — **"누가 막혀 있는가."**

## 3-2. 책임지지 않는 것 (경계)

> **08-03 회의 결정** — COO는 개념이 포괄적이라 그대로 두면 인사·경영지원·CEO 전략까지 확장된다.
> **"3인 스타트업"** 전제를 명시해 범위를 좁힌다.

## 3-2-1. 범위 밖 — 명시적 제외 (08-03 확정)

| 제외 영역 | 이유 |
|---|---|
| **인사** | 3인 팀에 채용·평가·노무 대상이 없다 |
| **경영지원** | 총무·법무·복리후생 대상이 없다 |
| **CEO 전략** | 제품·시장 방향은 3인 합의 사항이지 COO 단독 영역이 아니다 |

> 이 셋은 일반적인 COO 정의에는 포함되지만, **지금 우리 규모에서는 존재하지 않는 업무**다.
> 없는 일을 하려 들면 실제 병목(진도·품질·기록)에서 시간이 빠져나간다.

## 3-2-2. 역할 경계

| 안 하는 것 | 이유 | 대신 하는 것 |
|---|---|---|
| **코드 직접 수정** | CTO 영역 (팀 협업규칙에 명시) | 재현 가능한 버그 리포트까지 |
| **GitHub push** | **08-03 확정 — push는 CTO 전담** | 자료 정리해서 CTO에게 전달 |
| 제품 방향 단독 결정 | 3인 합의 사항 | 결정에 필요한 근거·데이터 제공 |
| 마케팅 메시지 작성 | CMO 영역 | 실행 일정·리소스 지원 |
| **남의 할 일 상태 임의 변경** | 시트 신뢰도가 무너진다 | 본인이 바꾸도록 요청 |

## 3-3. 파이프라인에서의 위치

3인의 작업은 병렬이 아니라 **순차 의존**이다.

```
전도준(기획·디자인)  →  윤은미(개발·배포)  →  최용우(QA·버그)
```

- 도준이 늦으면 **은미가 멈춘다**
- 은미가 멈추면 **용우가 볼 것이 없다**
- 용우의 리포트가 없으면 은미는 **무엇을 고칠지 모른다**

따라서 COO가 볼 지표는 *"은미가 지금 만들 것이 있는가"* 다.
은미가 대기 상태면 **도준의 앞단을 밀어주는 것**이 COO의 일이다. 은미를 재촉하는 것이 아니다.

## 4-2. 회의가 멈췄다

## 4-2-1. 원인 — 08-03 회의에서 확인됨

데이터만으로는 "과열 후 소진"으로 보였으나, 08-03 회의에서 실제 원인이 확인됐다.

> CTO: *"용우 님 신혼여행 가기 전까지가 우리가 열심히 한 것 같아요"* → CMO: *"맞아요, 다 같이 풀어졌어"*
> CMO: *"처음엔 열심히 했는데 허들이 높아지니까 기피하게 되고"*

**주된 기점은 COO의 결혼(7/4)·신혼여행이었고, 그 이후 관성으로 진도가 회복되지 않았다.** 07-01 회의록의 *"번아웃 방지 1일 1시간 리밋"* 도 배경으로 작용했으나, 구조적 만성 과부하는 아니었다.

> **이 구분이 중요하다.** 만성 과부하였다면 회의 빈도를 낮춰야 하지만, 일시적 이벤트였다면 오히려 **빈도를 높여 리듬을 복구하는 것**이 맞다. 08-03 회의에서 주 3회로 결정한 근거다(§6-1).
>
> COO의 초기 진단(소진)은 **원인을 잘못 짚었다.** 데이터는 *언제* 멈췄는지 알려주지만 *왜* 멈췄는지는 알려주지 않는다 — 그건 물어봐야 나온다.

## 4-4. 그 결과 문서 정합성이 깨졌다

상세 대조는 §2-3에 있다. 요약하면 — **시장조사 PDF와 레포·회의록은 같은 방향(외국인·지방 축제 여행팩)을 가리키는데, CMO 전략문서 00~09만 다른 방향(국내 포함·AI 콘텐츠 플랫폼)을 본다.**

주목할 점은 **그 PDF가 CMO 폴더 안에 있다는 것**이다. 즉 근거 자료는 확보되어 있는데 전략문서가 그 결론을 반영하지 못했다.

> **개인 실수가 아니라 기록 공백의 구조적 결과다.** 07-02~07-28 사이 동기화 지점이 하나도 없었고, 그 기간에 제품은 리브랜딩·MVP·배포까지 진행됐다. 각자 마지막으로 아는 버전에서 작업하면 이렇게 된다.
>
> **이것이 §5-4(문서-제품 동기화 지점)를 만든 이유다.** 사람을 탓하면 재발하고 구조를 고치면 재발하지 않는다.

## 4-7. 핵심 인사이트

1. 문제는 의욕이 아니라 **리듬**이다
2. **CTO에게 부하가 집중**되어 있다 (7월 산출물 사실상 1인)
3. **기록 공백 → 정합성 붕괴**로 이어진다 (CMO 문서 불일치가 증거)

5. **제품은 생각보다 앞서 있다.** 뒤처진 것은 운영이다

### git 권한 규칙 (08-03 확정) ★

| 역할 | 권한 |
|---|---|
| **CTO(윤은미)** | **push 전담** |
| COO · CMO | **pull만** |

CTO는 GitHub이 편하고 CMO는 아닐 수 있다. 하나로 강제하면 한 명이 안 쓰게 되고 그 순간 기록이 끊긴다.

# 7. 운영 체계 — 할 일 추적

진단 4-5의 구멍(추적률 0%)에 대한 해결.

## 7-1. 구조

**구글 시트 `팀_할일` 탭이 단일 원본.** 멤버별 탭은 `FILTER` 수식으로 연결된 **읽기 전용 미러**다(수동 복사 금지 — 반드시 어긋난다).

| 열 | 값 |
|---|---|
| ID | `CTO_1` `CMO_2` `COO_5` `Team_1` — 누구 것인지 즉시 식별 |
| 담당 | 윤은미 / 전도준 / 최용우 / 전원 |
| **상태** | `1-막힘` `2-진행` `3-대기` `4-완료` |
| 우선순위 | `1-높음` `2-보통` `3-낮음` |
| 할 일 / 기한 / 메모 / 링크 | |

숫자 접두어를 쓰는 이유 — 가나다 정렬 시 *낮음→보통→높음* 으로 뒤집히는 문제를 없애고, **정렬만으로 급한 것이 위로** 오게 하기 위함이다.

## 7-2. `막힘` 상태가 핵심인 이유

일반 칸반의 To do/Doing/Done은 COO에게 쓸모가 적다. COO가 볼 것은 하나다 — **누가 막혀 있는가.** 그것이 개입 지점이다.

## 7-3. 운영 규칙

1. 할 일이 생기면 **그 자리에서** 한 줄. 나중에 정리하지 않는다
2. **담당 없는 할 일은 만들지 않는다.** 정 없으면 `(미정)` + 다음 회의 안건으로
3. **기한은 비워도 된다.** 억지 기한은 지켜지지 않고 신뢰만 깎는다
4. **막힘은 부끄러운 게 아니라 신호다.** 이걸 문화로 못 만들면 시트는 죽는다
5. 시트 정리·정합성은 **COO 책임.** 팀원에게 *"시트 좀 채워주세요"* 라고 잔소리하지 않는다 — 회의를 듣고 COO가 채운다

## 7-4. 현재 적재 상태

07-29 액션아이템 12건 + COO 도출 항목 5건 = **17건 등록 완료.**
*빈 시트로 시작하지 않는 것이 핵심 — 빈 시트는 아무도 채우지 않는다.*

# 8. 운영 체계 — 품질(QA)

진단 4-6의 구멍(외부 검증 0회)에 대한 해결.

## 8-1. 대원칙

> **개발자가 재현할 수 있어야 한다. 재현되지 않는 버그는 고쳐지지 않는다.**

*"이상해요"* 는 리포트가 아니라 민원이다.

## 8-2. 양식 (GitHub Issue)

```
제목  [영역] 무엇이 어떻게 잘못됐나

1. 재현 절차   1) 2) 3)   + 재현율(5/5 · 2/10)
2. 기대 결과
3. 실제 결과   + 복구 방법 / "이 조건에선 정상"
4. 환경        기기·OS·브라우저·URL·시각
5. 증거        스크린샷 · 콘솔 에러 원문
```

**심각도** — `P0` 서비스/데모 불가(즉시) · `P1` 핵심 기능 파손 · `P2` 우회 가능 · `P3` 사소

팀 규칙이 *"모아서 한 번에"* 이나 **P0는 예외로 즉시** 알린다.

## 8-3. COO가 지킬 것

1. **원인을 추측해 쓰지 않는다.** 관측 사실만. 단 *"고양은 정상"* 처럼 **범위를 좁히는 관측은 최고의 정보**다
2. 올리기 전 중복 검색
3. **한 이슈에 한 버그** (묶으면 하나만 고치고 닫힌다)
4. 수정 후 **리포터가 재확인하고 닫는다**
5. 안 고칠 버그는 `wontfix` + 사유 한 줄 남기고 닫는다

## 8-4. 배포마다 도는 루틴

심사 데모 경로부터 완주한다. **이 경로는 버그 0이 목표.**

첫 진입 → 축제(목록·상세·지도) → 식당(지역·카테고리·검색) → 교통 → 로그인(카카오·구글·라인) → 모바일 실기기 → **외국어 경로(태국어·일본어·영문)** → 새로고침/뒤로가기 → 느린 네트워크

> 타겟이 외국인인 만큼 **외국어 경로 점검은 선택이 아니다.**

> ➋ **지역 특화 관광서비스 개발** ☞ *전국 단위 아닌 **1개 지역**(ex: 강원도, 충청남도, 부산, 강릉 등)에 특화된 서비스(**서울 제외**)*

**우리 상황 — 고양 + 공주 2개 지역이라 "1개 지역" 요건에 걸린다.**

| 지역 | 시도 | 가점(1개 지역) | **RTO 특별상** |
|---|---|---|---|
| 고양 | 경기도 | 단독 지정 시 가능 | ❌ **경기 해당 없음** |
| **공주** | **충청남도** | 단독 지정 시 가능 | ✅ **충남 대상** |

RTO 특별상 대상 지역: **부산·대전·광주·세종·충남·경북·강원·제주** (기관별 1팀)
→ *"경기 및 충북은 특별상 해당 사항 없음"*

> **판단: 공주(충청남도) 하나로 좁히면 가점 +2 + 충남 RTO 특별상 후보를 동시에 확보한다.**
> 고양은 둘 다 해당되지 않는다. **08-04 회의 1순위 안건.**
>
> 다만 이는 제품 범위 축소를 의미하므로 **COO 단독 결정이 아니라 3인 합의 사항**이다.

# 11. 자동화 로드맵

## 11-1. 원칙 — 자동화 대상은 하나씩

욕심내면 아무것도 못 끝낸다. **자동화 대상이 5개를 넘기 전까지 n8n 같은 별도 인프라는 도입하지 않는다.** 서버를 띄우고 유지보수하는 비용이 이득보다 크다.

## 11-2. 우선순위

| 순위 | 대상 | 상태 | 도구 |
|---|---|---|---|
| 1 | **할 일 추적** | ✅ 완료 | 구글 시트 |
| 2 | **회의록 파이프라인** — 녹음 텍스트 → 정리 → GitHub + 시트 | 🔄 진행 (08-03 COO 담당 확정) | Claude + 고정 프롬프트 |

| 4 | GitHub → 디스코드 알림 | 대기 | 웹훅 (설정만) |
| 5 | 공공데이터 갱신 감지 → 알림 | 검토 | GitHub Actions |
| 6+ | 이 시점에서 n8n 재검토 | — | — |

> 2·3번은 **08-03 회의에서 COO 액션아이템으로 확정**됐다. CMO 요청: *"미팅 자료를 어떤 기반으로 전략·정보를 추출하고, 어디에 자동화할지 설계해 달라."*

## 11-3. 폐기했다가 되살린 것 — 회의록 자동화

**폐기 → 부활.** 경위를 기록으로 남긴다.

| 시점 | 판단 | 근거 |
|---|---|---|
| 착수 | 자동화 1순위로 제작 | 회의록이 안 쌓이고 있었음 |
| 폐기 | 중복이라 접음 | CTO가 이미 녹화·정리 중임을 확인 |
| **부활 (08-03)** | **COO 담당으로 확정** | 회의록 정리가 CTO → COO로 이관됨. CTO는 개발에 집중 |

**현재 구조**

```
CTO 녹음(클로바노트) → 텍스트 변환 → COO 전달 → COO 정리 → CTO가 push
                                                    └→ 시트 `회의록` 탭
```

제작해둔 고정 프롬프트(팀 회의록 포맷 강제 + *"없는 내용을 지어내지 말 것"* 규칙)를 그대로 사용한다.

> **교훈 두 개.**
> ① 자동화 대상을 정하기 전에 **"이미 누가 하고 있는지"** 를 먼저 확인한다.
> ② 그러나 **폐기한 것을 지우지는 않는다.** 역할 분담이 바뀌면 되살아난다.

# 이 문서를 작성하면서 발견한 개선점

**① 팀 회고를 기억에 의존하지 말 것.**
보통 회고는 *"요즘 좀 느슨했죠"* 수준에서 끝나고 아무것도 바뀌지 않는다. 그러나 git log·회의록 파일명·이슈 수는 **이미 존재하는 객관 데이터**다. 집계에 10분이면 충분하고 인상보다 훨씬 정확하다. **본 진단(§4)을 월 1회 갱신한다.**

단, **커밋 수는 성과가 아니다.** 커밋이 적어도 설계·조사 중일 수 있다. 그래서 §14의 질문이 필요하다. 숫자는 *어디를 물어볼지* 알려줄 뿐 답까지 주지 않는다.

**② 역할 추가보다 경계 정의가 먼저다.**
07-29에서 C-level을 도입했지만 각 포지션이 **"무엇을 하지 않는가"** 는 정의되지 않았다. 3인 팀에서 역할이 늘면 책임이 늘어나는 게 아니라 **책임의 공백이 늘어난다.**

**③ 도구를 늘리면 기록이 준다.**
선택지가 늘면 *"이건 어디 적지?"* 라는 마찰이 생기고, 그 순간 아무 데도 안 적는다. 노션을 도입해도 카톡 결정은 여전히 증발한다. **도구 도입보다 배치표 합의와 이관 책임자 지정이 먼저다.**

**④ 문서 정합성 붕괴는 개인 탓이 아니다.**
CMO 문서가 06-30 이후 결정을 반영하지 못한 것은 성실성 문제가 아니라 **동기화 지점 부재**의 결과다. 그래서 §5-4에 정기 대조 장치를 넣었다. 사람을 탓하면 재발하고, 구조를 고치면 재발하지 않는다.
